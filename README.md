# ОРГАНИЗОВАННАЯ КУЛЬТУРНОСТЬ — сайт

**Версия: `orgculture-v58`**
**Обновлён:** 24.09.2026

## Правило версий

При каждой партии изменений сайта обязательно:
1. Поднять номер версии выше
2. Обновить дату
3. Дописать запись в `HISTORY.md` (сверху) — что именно поменялось и почему
4. Обновить «Что осталось доделать», если что-то закрылось или появилось

Версия архива (`orgculture-archive-vN`) считается отдельно — см. README
в корне полного архива.

## SITE_VERSION — держать в синхроне с версией сайта

В `gen.py` есть отдельная константа `SITE_VERSION` — она отвечает за
кэш-бастинг `style.css?v=N` и за номер кэша в `sw.js`. **Бампать её
вместе с версией из этого README при каждой правке**, иначе вернувшиеся
пользователи будут долго видеть старые стили (service worker кэширует
статику по стратегии cache-first).

## История изменений

Вынесена в **`HISTORY.md`** (с v57). Новая версия — новая запись
**сверху** в `HISTORY.md`, здесь только номер и дата в шапке.

## ⚠️ Правило при добавлении/удалении страницы

По образцу AELITA (`Site/README.md`). Новая страница — сразу же:
1. **sitemap.xml** — путь в `core_paths` (`build_sitemap()` в `gen.py`)
   **и** в `core` (`build_combined_sitemap()` в `gen_en.py`). Кроме
   юр. страниц из `NOINDEX_PATHS` — их в sitemap быть не должно.
2. **EN-двойник** в `gen_en.py` — иначе hreflang ведёт в 404.
3. **Хотя бы одна ссылка с сайта** — шапка (`header()`) или футер
   (`sections` в `footer()`), иначе страницу найдут только по адресу.
4. **`python3 ../check_archive.py`** — раздел 4.11 сверяет sitemap с
   папками, noindex и OG. Именно так в v57 нашлось, что `/contacts/`
   с v56 не была в sitemap.

## Неразрывные пробелы (с v58)

Последний шаг `gen.py` — `typography.py`: в видимом тексте русских
страниц обычный пробел меняется на неразрывный после коротких
предлогов/союзов («в театре», «и на»), перед «же/ли/бы», перед тире,
между числом и единицей, после «№», в инициалах и сокращениях. На
телефоне предлоги больше не висят в конце строки. Перенесено из пака
AELITA (pack-v485) с одной поправкой — см. комментарий в
`transform_html()`.
- **В `gen.py` и `texts_*.json` неразрывные пробелы руками не
  ставить** — пиши обычные, сборка расставит сама.
- `<head>`, атрибуты, `<script>`, `<style>`, `<svg>`, EN-страницы — не
  трогаются.
- Проверка — `check_archive.py`, раздел 4.12 (страница собрана в обход
  или сборка упала до конца — будет видно).
- Посмотреть, что стало с одной страницей:
  `python3 typography.py texts/eyforiya`.

## Аналитика

Три слоя, все — только после «Хорошо» в cookie-баннере
(`ok_cookie_consent === '1'`):
- **Яндекс.Метрика** `111176053` — `yandex_metrika_snippet()`.
- **Свой маячок** на воркер (`/track`) — `own_stats_snippet()`,
  просмотры + UTM; отчёт раз в неделю от бота.
- **Цели** (с v57) — `assets/analytics-events.js`, генерируется из
  `ANALYTICS_GOALS` в `gen.py`. Клики ловит один обработчик по адресу
  ссылки; формы зовут `window.okTrack('…')` сами после успешной
  отправки. Каждая цель уходит и в Метрику (`reachGoal`), и в воркер
  (`ev:<неделя>:<имя>`, блок «Действия на сайте» в отчёте).

| Цель | Когда |
|---|---|
| `brief_submit` | отправлен бриф на `/contacts/` |
| `offer_download` | скачано КП (RU/EN PDF) |
| `cv_download` | скачано CV |
| `press_kit_download` | скачан файл из `documents/press/` |
| `telegram_channel_click` | переход в t.me/orgculture |
| `telegram_bot_click` | переход в бота, в т.ч. из плавающего виджета |
| `vk_click` | переход в VK |
| `email_click` | клик по mailto: |
| `review_submit` | отправлен отзыв на текст |
| `rss_click` | клик по RSS |

**Один раз руками в Метрике:** «Цели» → «Добавить цель» →
«JavaScript-событие», идентификатор — имя из таблицы. Без этого
`reachGoal` приходит, но в отчётах целей не видно.
**Новая цель** = имя в `ANALYTICS_GOALS` (`gen.py`) **и** в
`TRACK_EVENTS` (`04-bot/worker.js`) — воркер незнакомые имена
отбрасывает — **и** цель в Метрике.
Не отслеживается сознательно: скролл/«дочитал текст» (как и у AELITA
— отдельное решение), бриф через бота (его считает сам бот —
«Заявки с формы брифа» в отчёте).

## Логотип и написание — не шрифт, а векторная конструкция

Знак (эллипс О + К) и всё написание в hero-блоке главной страницы нарисованы
напрямую в SVG, встроены инлайн на каждой странице, где нужны (шапка сайта —
только знак, главная — знак + полное написание). Пропорция эллипса везде
одна: **rx 200 : ry 110**. Если нужно изменить толщину линии, размер или
пропорцию знака — правится в одном месте, `gen.py` (переменные
`LOGO_MARK_SVG` / `WORDMARK_DEFS`), сайт нужно пересобрать заново
(`python3 gen.py`), а не редактировать сгенерированные HTML-файлы вручную.

## `gen.py` — сайт генерируется, не пишется руками

Все 57 генерируемых RU HTML-файлов (на v57) собраны одним Python-скриптом
(`gen.py`): 38 текстов + 6 страниц проектов + 13 остальных (главная,
тексты, проекты, манифест, рекомендации, автор, продюсирование,
контакты, для прессы, политика, cookie, правила бота, офлайн-страница).
EN-зеркало — `gen_en.py`. Собираются из:
- общих функций шапки/футера/карточки (`page_head`, `header`, `footer`, `card`),
- списка текстов `TEXTS` (заголовок, тег, кикер, абзацы, метаинформация, ссылка, картинка),
- списка пунктов манифеста `MANIFESTO_POINTS`,
- списка опыта `CV_ROLES` для страницы «Об авторе».

**Если нужно добавить/поправить текст** — редактируется словарь в `TEXTS`
внутри `gen.py`, затем `python3 gen.py` пересобирает весь сайт (текст,
индекс текстов, рекомендации и главную — они все ссылаются на один и тот же
список). Редактировать HTML в `texts/<slug>/index.html` напрямую не нужно —
при следующей пересборке правка потеряется.

**`texts-manifest.json`** — побочный файл, который `gen.py` пишет при
каждой сборке (список `slug` + `title` всех текстов). Это не часть
сайта, а единственный источник правды для списка текстов в
Telegram-боте — см. `04-bot/sync_texts.py`. **Если добавляешь текст —
после `gen.py` обязательно запускай ещё и `sync_texts.py` из `04-bot/`**,
иначе бот не узнает о новом тексте (команда «🎲 Случайный текст» его
просто никогда не покажет, без явной ошибки).

## Тексты: как устроены и что было сделано при переносе

Исходные тексты (посты из соцсетей) перенесены с лёгкой правкой: убраны
явные опечатки и тавтологии, добавлена единая структура (тег-категория,
короткий кикер под заголовком, блок с источником/датой/ссылкой внизу).
Голос и структура абзацев автора сохранены как есть — переписывался не
смысл, а шероховатости.

Ссылки на «где посмотреть/послушать» сохранены там, где были в оригинале
(Beat Film Festival, musicAeterna, Instagram «Робота Кости», Кинопоиск HD,
театр им. Ленсовета). Там, где в оригинальном посте ссылки не было
(«Аннетт», «Герда», «Ход королевы», «Высокое разрешение», «Майя
Плисецкая», «Интервью В», «Нет нужды писать») — она и не добавлена;
на странице рекомендаций для таких текстов кнопка ведёт на сам текст,
а не на внешний сервис.

## Бегущая строка (marquee)

На главной странице под hero-блоком — плакатная бегущая строка со слоганом,
приём в духе референса koroche.ru, но на своих цветах (терракотовый фон,

строкой в `build_index()`. Если приём приживётся — можно так же добавить
на страницы текстов или в шапку сайта целиком.

## Проверка после правок

`sitemap.xml`, `feed.xml` и `texts-manifest.json` теперь пересобираются
автоматически при каждом запуске `gen.py` — вручную сверять их со
списком папок в `texts/` больше не нужно. **`sitemap.xml` пересобирается
ещё раз, уже с англ. hreflang-парами, внутри `gen_en.py`** — если
запускаешь только `gen.py` без `gen_en.py`, sitemap останется без
английских URL.

Что проверить после добавления текста:
1. `python3 gen.py` отработал без ошибок и написал все файлы;
2. добавлен перевод нового текста в `texts_en.json` (тот же slug), затем
   `python3 gen_en.py` — иначе английская версия останется без него;
3. запущен `python3 sync_texts.py` из `04-bot/` — иначе бот не узнает
   о новом тексте;
4. `SITE_VERSION` в `gen.py` и версия в шапке этого README подняты;
5. `BUILD_DATE` в `gen.py` обновлён — от него зависят `lastmod` в
   sitemap и `lastBuildDate` в RSS (в обеих лентах, `feed.xml` и
   `en/feed.xml`);
6. **`gen_en.py` запущен после `gen.py`, а не вместо него** — иначе
   `sitemap.xml` и `sw.js` останутся в урезанных RU-only версиях (оба
   файла `gen_en.py` пересобирает заново поверх того, что написал
   `gen.py`);
7. **`python3 check_en.py` — чисто.** Ловит то, что легко упустить при
   правке одного текста: перевод обрезан относительно оригинала, тег
   переведён не по канону, имя/название написано не так, как везде.
   Если добавлялось новое повторяющееся имя — стоит на всякий случай
   занести его в `glossary_en.json` (`locked_terms`), тогда проверка
   будет следить и за ним тоже.

### 1. Сделать можно сразу — данных от тебя не нужно

**1.1. Цели Метрики на ключевые действия.** У AELITA —
`assets/analytics-events.js`: один делегированный обработчик кликов,
12 именованных целей (`reachGoal`), грузится только после согласия на
cookie, те же события дублируются в их собственную статистику. У нас
счётчик `111176053` стоит, но **ни одной цели нет** — Метрика видит
визиты, но не видит, сработал ли сайт как витрина продюсера.
Предлагаемый набор (без выдуманных категорий, только то, что есть на
сайте):
- `brief_submit` — отправка формы брифа на `/contacts/` (главная цель);
- `offer_download` — скачивание КП (PDF) с `/production/`;
- `cv_download` — скачивание CV;
- `telegram_channel_click`, `vk_click` — переходы в соцсети;
- `telegram_bot_click` — переход в бота (в т.ч. из плавающего виджета);
- `email_click` — клик по почте;
- `review_submit` — отправка отзыва на текст;
- `rss_click`, `pwa_install_click` — подписка на RSS / установка PWA.
Те же события — в наш маячок воркера (как у них — в свою таблицу).
Отдельно по опыту AELITA (pack-v101): у них нашлись страницы, где
скрипт целей просто не был подключён, — поэтому сразу нужна проверка
в `check_archive.py`, что файл подключён на каждой публичной странице
RU и EN (расширить существующую `check_analytics_present`).
Скролл/«дочитал текст» — у AELITA сознательно отложено; у нас это
было бы полезнее, чем у них (сайт текстов), но это отдельное решение.

**1.2. Футер как у AELITA — разделы + контакт + статус.** Сейчас в
футере только Telegram/VK и юр. ссылки: нет ни навигации по разделам,
ни почты, ни указания, с кем заказчик имеет дело. У AELITA в футере —
список «Разделы» и реквизиты с контактом. Для нас: «Тексты · Проекты

будет. Правится в одной функции `footer()` в `gen.py` (+ EN в
`gen_en.py`).

**1.3. Юридические страницы — закрыть от индексации.** У AELITA
`/privacy`, `/cookies`, `/bot`, `/oferta` закрыты в `robots.txt` и не
входят в `sitemap.xml` — осознанно. У нас `/privacy/`, `/cookies/`,
`/bot-rules/` (и EN-двойники) сейчас в sitemap и открыты. Предложение:
убрать из генерации sitemap, добавить `Disallow` (или `noindex` в
`<head>` — надёжнее для Яндекса, т.к. `Disallow` не убирает уже
проиндексированное). Ссылки в футере остаются.

**1.4. `og:image` в пропорции 1200×630.** Правило AELITA (aelita-v47):
превью для соцсетей — всегда ~1.91:1, отдельным файлом

### 3. Документация и проверки

**3.1. Разделить README сайта на инструкцию и журнал.** У AELITA
`Site/README.md` — правила и устройство, `Site/HISTORY.md` — журнал
правок. У нас в этом README ~970 из ~1190 строк — история; нужные
правила («Проверка после правок», устройство `gen.py`) теряются в
конце. Предложение: вынести историю в `03-website/HISTORY.md`, в
README оставить версию + ссылку. (Попутно в этом заходе уже
исправлено: запись v55 была приклеена в конец файла — перенесена на
место в историю; пункт «Нет форм обратной связи» помечен устаревшим.)

**3.2. Правила-«шлагбаумы» в начало README** — как у AELITA
(«⚠️ Правило при добавлении/удалении страницы»): новая страница =
sitemap (кроме закрытых), хотя бы одна ссылка с сайта, EN-двойник,
запись в `sw.js`, если нужна офлайн.

**3.3. Новые проверки в `check_archive.py`** (у AELITA это категории
`run_audit.py`): папки сайта ↔ `<loc>` в `sitemap.xml` один в один;
полный набор OG-тегов на каждой публичной странице + пропорция
`og:image` (у AELITA это «стоит завести» — у нас можно сразу);
подключение скрипта целей (см. 1.1).

### Смотрели и сознательно не предлагаем
Билеты, оплата ЮKassa, подарочные карты, личный кабинет, админка,
сканер QR на входе, гостевая система — у нас нет продаж и
мероприятий на своём домене. Страницы персон/лекций — не наш формат.
Cloudinary — картинок мало, лежат в репозитории, этого хватает.
Пиксель VK Рекламы — имеет смысл только если пойдёт платная реклама
в VK; тогда взять их схему (грузить только после согласия на cookie,
`VK_PIXEL_ID = 0` — не грузить вовсе, а не ставить заглушку).
